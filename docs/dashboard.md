# The LFG dashboard (`lfg ui`)

A local web page at http://127.0.0.1:7777 that shows what LFG is doing in your repos and lets you control it. It loads nothing from outside your computer. The pages live in `plugin/lib/lfgcore/ui_assets/` and use plain-language labels. Navigation is a side menu, and old view hashes (`#overview`, `#reviews`, `#brain`, …) redirect.

## Pages

| Page | What it shows |
|---|---|
| Home | The current run, the next step, and what needs you |
| Runs | Every run, with a one-paragraph description from its brief (or review summary). Run files (review, security, pentest, tasks, checks, ship check) are shown as readable text, never raw JSON, and failed checks show their output |
| Issues | The dev-graph mirror of Linear, for the chosen repo and branch. dev-graph issues carry no repo, so LFG ties them from local evidence: a run of the repo names the issue (run.json, tasks.json, brief or design; the issue is on that run's branch), a local branch name holds its tracker key, or its description says `Repo: <name>`. A task whose run marked it passed shows as done. Stale = open and untouched for 14+ days. An issue saved without its text (empty, or a bare `Repo: … Run …` pointer) shows its task's description, steps and verification, or the run brief's Problem and Acceptance criteria, marked as coming from the run. Home's issue counts use the same scope |
| Reviews | Pull requests in the chosen repo that ask for your review (`gh pr list --search review-requested:@me`, cached 5 minutes; **Refresh** asks GitHub again). **Start review** fetches the PR head and base into `refs/lfg-review/pr-<n>[-base]` (never a branch) and checks the head out detached in its own worktree, `<repo>.worktrees/review-pr-<n>` (its name is shown; the idle clean-up skips it), so your checkout is never touched. A background `claude -p` session in that worktree, started with the repo's `.claude/settings.local.json` so LFG's skills, brains and guard are on, runs the lfg:expert skill in PR mode (read-only tools, no Edit/Write; model `models.expert-review`) and returns a grilling review: summary, a 1-5 rating per area with reasons, questions for you, draft comments on changed lines, and the dev-graph/second-brain context it used. **Talk it through** continues the same session; its draft changes merge into yours, keeping your scores, answers and include switches. You set your own ratings, edit or drop comments, pick Comment / Request changes / Approve, and **Review and post** shows exactly what goes out (comments on diff lines go inline, the rest into the summary). Only **Post to GitHub**, after a confirm, sends it: one review through `gh api`, refused if it looks like it holds a secret. **Pull new commits** moves the worktree to the new head and asks the AI to re-check; **Done** removes the worktree and refs, keeping the chat and draft. **Your pull requests** (second tab, `gh pr list --author @me`): **Read the comments** gathers every thread someone else started (GraphQL `reviewThreads` with resolved/outdated, plus review summaries and general comments from people; bots' inline comments count, their summaries and notices don't, hidden `<!-- -->` bot state is stripped) and the AI, in the same kind of worktree, checks each against the code, graphs and brains in the expert skill's comment triage mode: how likely it is worth fixing (0-100%) and why, the fix, a ready reply for fixing it, one for not fixing it, and 2-4 alternative reasons. You pick Fix / Won't fix / Skip (a reason swaps its reply in), edit, and **Review and post replies** sends each as a reply under its comment (an inline thread reply, or a quoted PR comment); each is marked posted so it never goes twice. Refresh reads new comments and analyses only those. Starting, talking, posting and removing need the unlocked dashboard. |
| Checks | Review, security, ship check, and actions the guard stopped. With the SonarQube pack, a SonarQube tab: the local quality gate and its failed conditions, issues on lines this branch changed first (the rest folded away), SonarCloud's own verdict for the commit from GitHub, and **Scan now** (background `lfg sonar scan`, unlocked dashboard) |
| Code | Graph views and architecture health. The code map can be built, updated, rebuilt or its docs refreshed here (see *Code map* below) |
| Docs | A tree. **Project**: LFG's Wiki (onboarding tour, landmines, test gaps, playbooks from /learn), the glossary, Decisions (ADRs) and docs you asked LFG to write. **Branches**: one folder per branch for docs about that branch's work (current branch first and open). The repo's own markdown and graphify's per-cluster pages aren't listed |
| Knowledge | dev-graph and second-brain. Click any entry for its full text: a decision's context, choice and consequences; a rule's why, alternative and source; a gap's today and goal; a note's whole text |
| Usage | Per repo, "did Claude use LFG?": how many of the last 30 days' replies used an LFG skill, only LFG's tools, didn't use LFG (with the reason Claude gave), or didn't say, plus the latest deviations. Dollars spent today, over 7 and over 30 days, and by model, as `tokensave cost` works them out from Claude Code's session logs at API prices. Shown only when tokensave is installed and its upload counter is off. Also Headroom's own estimate of what compression saved. Both tools run in the background, one process at a time |
| Skills | Every skill Claude Code loads on this computer: personal, personal commands, the selected project's and every installed plugin's (LFG's included). For each skill: how to type it, where it comes from, name clashes (the short name goes to your own skill first, so plugin skills need their full `/plugin:name`), how much context its description costs, and a switch for whether Claude may use it on its own (`disable-model-invocation`; your personal skills are edited in place with a backup, LFG's are saved as overrides). The **Edit LFG skills** tab is the Markdown editor for LFG's skills |
| Integrations | One card per integration: Core (code graphs), Knowledge graphs (dev-graph, second-brain; Restart), Headroom (mode, port, which sessions it routes), SonarQube (open it, share-usage-stats switch, off by default, applied with a restart that keeps the login and results), Dictate (shortcut, typing or pasting, clean-up), Pentest (Strix with a local Ollama model: max turns, Ollama URL and the model manager), Security scanners (company domains, private scopes), Ship check (container memory, CPUs, health timeout, build-cache pruning), Linear (team, workspace) and GitHub (sign-in, read-only). Each shows its live status; **Turn on** installs it in the background with a log, **Turn off** stops it (tools stay installed). Settings save as you change them (unlocked dashboard). The command-line tools LFG uses are listed at the bottom |
| Settings → Claude Code | Where LFG is on (per repo, or every repo); the guard, commit approval and hardened mode; the MCP servers LFG brings; your Claude Code setup (read-only); and every change LFG made outside `~/.lfg`, each undoable. Feature packs and Headroom moved to Integrations |
| Settings → General | The `~/.lfg/config.json` settings that belong to no integration (dashboard port, disk space, lanes, models, commit approval, whether replies say they used LFG); each integration's own settings are on its card |
| Settings → Disk space | `~/.lfg` disk use against `storage.limit_mb` (default 500; graphs inside repos are shown separately and not counted). Deletable items: runs on branches that were merged or deleted, everything for repos whose folder is gone, graphs not synced for `storage.idle_graph_days` (default 30), generated graph visualisations. The current run and the checked-out and default branches are never offered |
| Settings → Rules | The 18 standing rules (read-only, enforced in code) and the rule modules, which you can change in Markdown or add to (saved in `~/.lfg/overrides/rules/`; undo and delete keep a backup). Any mention of a rule anywhere in the dashboard shows what it means on hover |
| Settings → Your instructions | `~/.claude/CLAUDE.md`, formatted, with an editor. LFG never writes to it otherwise |
| Help | The guide, every skill and agent, the CLI reference and the sharing guide |

The project picker shows each repo's folder name. The branch picker marks the checked-out branch and filters Home, Runs and Checks by the branch each run recorded (`run.json` `branch`). Graphs stay one per repo and follow the checked-out branch.

## Editing and safety

- **Read-only unless unlocked.** `lfg ui` opens the browser with the local edit key in the URL fragment. The key is a 0600 file in `~/.lfg/ui/`, never printed, and the guard keeps agents away from it. `lfg ui --unlock` re-opens a running dashboard unlocked.
- **What every write needs:** the key, the same Origin, the `X-LFG: 1` header and a JSON body. Writes are validated, refused if they look like a secret, backed up to `~/.lfg/backups/`, and audited.
- **Changes to Claude Code go through the change ledger,** exactly like the same change made with the CLI, so `lfg uninstall` can undo them. This covers turning a repo on or off, hardened mode, Headroom scope and packs.
- **Skill edits** live in `~/.lfg/overrides/skills/` and are written to the installed plugin, which Claude Code loads in place. Updates keep them, and pristine copies are in `~/.lfg/defaults/skills/`.
- **Deletes** (Disk space) stay inside `~/.lfg` or a known repo's graph folders.
- **Reading the API** needs the `X-LFG: 1` header, and the Host must be 127.0.0.1 or localhost (guards against DNS rebinding).

## Code map

The code map can be built, updated or rebuilt from scratch, and its docs refreshed, from the side menu, Home and Code. This uses `POST /api/save/graphs_build`, the same background job the hooks start. It needs no edit key, but it does need the same Origin, Host and header checks.

A run can span repos: its tasks.json gives each task a `repo`. A run is listed under its own repo and, under All branches, under every other repo its tasks name (matched on the folder name or its last part, so `portal` means aegis-compliance-portal), marked "filed under <repo>" with that repo's task count. There it shows that repo's part only: the brief, design and task list count as shared, build counts once that repo's tasks all pass, and the owner's checks, review and ship files neither count nor show; its run page lists that repo's tasks. Issues for those tasks show under that repo too.

A run's checks (`ready.json`: lint, types, tests, build) show only in the repo the run is filed under. When the run's build notes, patches or task list changed after the checks ran, the result shows as out of date (rerun `/lfg:check`) instead of passing or failing.

In a run filed under another repo, a repo's own stage results carry its name: `04-qa-<repo>.md`, `ready-<repo>.json`, `05-secure-<repo>.json`, `05-pentest-<repo>.json`, `06-review-<repo>.json`, `07-shipcheck-<repo>.json`. They show on that repo's Checks page and count toward its progress; the owner repo only reads the unsuffixed files.
