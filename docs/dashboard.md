# The LFG dashboard (`lfg ui`)

A local web page at http://127.0.0.1:7777 that shows what LFG is doing in your repos and lets you control it. It loads nothing from outside your computer. The pages live in `plugin/lib/lfgcore/ui_assets/` and use plain-language labels. Navigation is a side menu, and old view hashes (`#overview`, `#reviews`, `#brain`, …) redirect.

## Pages

| Page | What it shows |
|---|---|
| Home | The current run, the next step, and what needs you |
| Runs | Every run, with a one-paragraph description from its brief (or review summary). Run files (review, security, pentest, tasks, checks, ship check) are shown as readable text, never raw JSON, and failed checks show their output |
| Issues | The dev-graph mirror of Linear, for the chosen repo and branch. dev-graph issues carry no repo, so LFG ties them from local evidence: a run of the repo names the issue (run.json, tasks.json, brief or design; the issue is on that run's branch), a local branch name holds its tracker key, or its description says `Repo: <name>`. A task whose run marked it passed shows as done. Stale = open and untouched for 14+ days. An issue saved without its text (empty, or a bare `Repo: … Run …` pointer) shows its task's description, steps and verification, or the run brief's Problem and Acceptance criteria, marked as coming from the run. Home's issue counts use the same scope. **Your epic and stacks** (top of the page): the epic or parent ticket holding the work in front of you (the current run, else the checked-out branch), its tickets in build order (after any ticket that blocks them, then by where each PR sits in its stack, then ticket number), each with its status, PR, place in the stack and LFG run, with **You are here** and **Next**; a PR merged into the default branch counts as done. Below it, every stack of PRs in the repo |
| Stack strip | On a run page and a PR's review page: the stack the PR is in, bottom first, each PR's ticket, state (draft, open, approved, changes asked, merged into the PR below, merged into main), CI and CodeRabbit, and how many commits it is behind the branch below; then one line about the epic and what's next. GitHub's own stacks come from each PR's base branch; a **preview stack** also shows your recent branches with no PR yet, or a PR still aimed at main, built on another branch (from local git). Read only: `gh` (cached 2 minutes), local git and dev-graph's copy of Linear, the same sources the other pages use. One component (`stackBox`) serves all three places |
| Checks | Review, security, ship check, and actions the guard stopped. With the SonarQube pack, a SonarQube tab: the local quality gate and its failed conditions, issues on lines this branch changed first (the rest folded away), SonarCloud's own verdict for the commit from GitHub, and **Scan now** (background `lfg sonar scan`, unlocked dashboard) |
| Code | Graph views and architecture health. The code map can be built, updated, rebuilt or its docs refreshed here (see *Code map* below) |
| Insights | From git history only, nothing fetched. **Hotspots**: files that keep needing fixes in the last 180 days (fix commits, changes, how many people touch it, size, whether a test covers it), each with its reasons, recent fixes and whether fixes are rising; generated files left out; and the same by folder. **Why is this here**: the commits that shaped a file or a range of its lines, newest first, with the PRs, issues and Linear tickets they mention as links. Only files git knows can be read. Also `lfg hotspots` and `lfg why <file>[:start-end]`. Ported from upstream LFG |
| Docs | A tree. **Project**: LFG's Wiki (onboarding tour, landmines, test gaps, playbooks from /learn), the glossary, Decisions (ADRs) and docs you asked LFG to write. **Branches**: one folder per branch for docs about that branch's work (current branch first and open). The repo's own markdown and graphify's per-cluster pages aren't listed |
| Knowledge | dev-graph and second-brain. Click any entry for its full text: a decision's context, choice and consequences; a rule's why, alternative and source; a gap's today and goal; a note's whole text |
| Usage | What Claude Code used and what it would cost at Anthropic's API list prices, worked out from Claude Code's own session transcripts (`~/.claude/projects`, subagents included): per day or week, per model, PR review sessions, today, the last 7 and 30 days and the chosen range. Each request is priced on its own, so a model whose price depends on prompt size (Claude Haiku 5.5 above 100K tokens) is priced right. A model LFG has no price for counts as $0 and is named under "Not priced". It counts every Claude Code session on this computer, including repos where LFG is off. Headroom's detail view shows what compression saved, per day and per hour today, from `~/.headroom/savings_events.jsonl`. When "Say whether LFG was used" is on (Settings → General, off by default): per repo, how many of the last 30 days' replies used an LFG skill, only LFG's tools, didn't use LFG (with the reason Claude gave), or didn't say, plus the latest deviations |
| Sessions → What it changed | Every file a session edited, as diffs, from its own transcript (not git, so other sessions' and your own edits don't mix in); denied and rewound edits are left out, edits in the repo's worktrees count as the project's, and shell commands that may have written files are listed. Click a line number, then shift-click another, to pick lines and **Ask** about them (answers only) or **Make this change** (edits files); it goes to the session as a skill run, in a copy unless you pick the session itself. Sessions touched in the last 6 hours also show their **background work**: subagents (type, steps, what each is doing now) and background commands, running or finished in the last 20 minutes; work silent for 15 minutes shows as no news. Ideas from upstream LFG's Studio |
| Skills | Every skill Claude Code loads on this computer: personal, personal commands, the selected project's and every installed plugin's (LFG's included). For each skill: how to type it, where it comes from, name clashes (the short name goes to your own skill first, so plugin skills need their full `/plugin:name`), how much context its description costs, and a switch for whether Claude may use it on its own (`disable-model-invocation`; your personal skills are edited in place with a backup, LFG's are saved as overrides). The **Edit LFG skills** tab is the Markdown editor for LFG's skills |
| Integrations | **Claude Code plugins** (below the cards): the plugins you installed, each with an on/off switch and Remove (a plugin installed for one repo only is shown, and changed in that repo's Claude Code); suggested plugins; and a search of every plugin in the marketplaces Claude Code knows, with Install. All through `claude plugin … --scope user`; an install is in the change list (Settings → Claude Code). One card per integration: Core (code graphs), Knowledge graphs (dev-graph, second-brain; Restart), Headroom (mode, port, which sessions it routes), SonarQube (open it, share-usage-stats switch, off by default, applied with a restart that keeps the login and results), Dictate (shortcut, typing or pasting, clean-up), Pentest (Strix with a local Ollama model: max turns, Ollama URL and the model manager), Security scanners (company domains, private scopes), Ship check (container memory, CPUs, health timeout, build-cache pruning), Linear (team, workspace) and GitHub (sign-in, read-only). Each shows its live status; **Turn on** installs it in the background with a log, **Turn off** stops it (tools stay installed). Settings save as you change them (unlocked dashboard). The command-line tools LFG uses are listed at the bottom |
| Tabs | Every PR review and Studio session you open becomes a tab: a row above the page and a list under PR reviews or Studio in the sidebar. Drag one in either place to reorder; both follow one order. **Pin** one (the pin on hover) to keep it at the front: pinned tabs stay ahead of the rest, have no close button, and are never dropped when you have many open. Each repo has its own tabs: the ones shown are the repo selected top left's (a PR's tab shows wherever you have no checkout of its repo); dragging a tab among the pinned ones pins it, dragging it out unpins it. Studio's sidebar shows your tabs first, then live sessions that aren't open as tabs. Kept in this browser |
| Corrections | What you corrected Claude on, and the switch that turns capturing on or off (off by default). Each queued item shows what you said, what Claude had just done, why LFG caught it and, when Claude queued it, its read of the lesson. **Approve as a rule** with the wording, an optional why and real example (both told to Claude with the rule), for every repo or only the repo it was said in; **Merge into it** when LFG finds a rule of yours that says much the same; **Save to second-brain** for background about you rather than how Claude should work; **Discard**. Below: the rules that came from corrections, each with its switch, how many corrections it holds and editable wording. Nothing becomes a rule until you approve it here or with `! lfg corrections approve` |
| What's new | Once after you install a new release, before anything else is offered: a walkthrough of what changed. The first step lists it all; each step after opens the page the item is about and lights up the part it means. Skip any time; finishing or skipping counts the release as seen. A first install skips it (the setup guide comes first). Written in `plugin/releases.json` |
| Settings → Claude Code | Where LFG is on (per repo, or every repo); the guard and hardened mode; the MCP servers LFG brings; your Claude Code setup (read-only); and every change LFG made outside `~/.lfg`, each undoable. Feature packs and Headroom moved to Integrations |
| Settings → General | The `~/.lfg/config.json` settings that belong to no integration (dashboard port, disk space, lanes, models, whether replies say they used LFG); each integration's own settings are on its card |
| Settings → Connections | Everything LFG connects to, every MCP server Claude Code has (connected, or waiting for a sign-in), and any command-line tool LFG uses that isn't installed |
| Settings → Disk space | `~/.lfg` disk use against `storage.limit_mb` (default 500; graphs inside repos are shown separately and not counted). Deletable items: runs on branches that were merged or deleted, everything for repos whose folder is gone, graphs not synced for `storage.idle_graph_days` (default 30), generated graph visualisations. The current run and the checked-out and default branches are never offered |
| Settings → Rules | The 18 standing rules (read-only, enforced in code) and the rule modules, which you can change in Markdown or add to (saved in `~/.lfg/overrides/rules/`; undo and delete keep a backup). Any mention of a rule anywhere in the dashboard shows what it means on hover |
| Settings → Your instructions | `~/.claude/CLAUDE.md`, formatted, with an editor. LFG never writes to it otherwise |
| Help | **What's new**: every release, newest first, in plain words, each with **Walk me through it**. The guide, every skill and agent, the CLI reference and the sharing guide |

The project picker shows each repo's folder name. The branch picker marks the checked-out branch and filters Home, Runs and Checks by the branch each run recorded (`run.json` `branch`). Graphs stay one per repo and follow the checked-out branch.

## Editing and safety

- **Read-only unless unlocked.** `lfg ui` opens the browser with the local edit key in the URL fragment. The key is a 0600 file in `~/.lfg/ui/`, never printed, and the guard keeps agents away from it. `lfg ui --unlock` re-opens a running dashboard unlocked.
- **What every write needs:** the key, the same Origin, the `X-LFG: 1` header and a JSON body. Writes are validated, refused if they look like a secret, backed up to `~/.lfg/backups/`, and audited.
- **Changes to Claude Code go through the change ledger,** exactly like the same change made with the CLI, so `lfg uninstall` can undo them. This covers turning a repo on or off, hardened mode, Headroom scope and packs.
- **Skill edits** live in `~/.lfg/overrides/skills/` and are written to the installed plugin, which Claude Code loads in place. Updates keep them, and pristine copies are in `~/.lfg/defaults/skills/`.
- **Deletes** (Disk space) stay inside `~/.lfg` or a known repo's graph folders.
- **Reading the API** needs the `X-LFG: 1` header, and the Host must be 127.0.0.1 or localhost (guards against DNS rebinding).

## Pages that update themselves

A page watching something (a running review, checks, a scan, a Claude session) redraws every 1.2 to 15 seconds. A
redraw changes only what changed, so what you opened, scrolled to, selected, typed or attached stays as it was, and a
chat stays at its end only if you were at its end. For anyone changing `app.js`:

- Redraw with `morph(el, html)` (or `softRoute()` for the whole page), never `el.innerHTML =` on a timer or poll.
- Content script draws into an element (a table, a tab's body, the review chat) is marked `data-fill` in the HTML; an
  element script adds (the Rewind box) is `data-local`; attributes script toggles go in `data-keep="hidden ..."`.
- A `<details>`'s `open`, typed text and a style script set always stay. Tables, charts and logos are numbered from 1
  each time a page draws, so a redraw finds the same ones (and keeps a table's sort and filter).
- Wiring runs again on elements a redraw kept: use `el.onclick = ...`, or guard `addEventListener` with
  `once(el, "what")`. Page timers go through `pageTimer(name, ms, fn)`, one pending per name.

After an Update, every open dashboard tab moves to the new version, not only the one you pressed Update in. The page
carries a fingerprint of the dashboard's files it loaded (`<meta name="lfg-build">`), and `GET /api/update` returns
the installed one (`build`). When they differ, the tab reloads itself, or, while you're typing, shows a Reload button.

## Code map

The code map can be built, updated or rebuilt from scratch, and its docs refreshed, from the side menu, Home and Code. This uses `POST /api/save/graphs_build`, the same background job the hooks start. It needs no edit key, but it does need the same Origin, Host and header checks.

A run can span repos: its tasks.json gives each task a `repo`. A run is listed under its own repo and, under All branches, under every other repo its tasks name (matched on the folder name or its last part, so `portal` means aegis-compliance-portal), marked "filed under <repo>" with that repo's task count. There it shows that repo's part only: the brief, design and task list count as shared, build counts once that repo's tasks all pass, and the owner's checks, review and ship files neither count nor show; its run page lists that repo's tasks. Issues for those tasks show under that repo too.

A run's checks (`ready.json`: lint, types, tests, build) show only in the repo the run is filed under. When the run's build notes, patches or task list changed after the checks ran, the result shows as out of date (rerun `/lfg:check`) instead of passing or failing.

In a run filed under another repo, a repo's own stage results carry its name: `04-qa-<repo>.md`, `ready-<repo>.json`, `05-secure-<repo>.json`, `05-pentest-<repo>.json`, `06-review-<repo>.json`, `07-shipcheck-<repo>.json`. They show on that repo's Checks page and count toward its progress; the owner repo only reads the unsuffixed files.
